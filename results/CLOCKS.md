# Step 2: matched-delay clock calibration

To compare recipes on area fairly, every recipe must be judged at the same, timing-
legal operating point. At each design's shipped clock, six of nine corpus designs
miss timing (see `results/BASELINE.md`), which contaminates area. So we calibrate a
per-design clock period at which the reference resyn2 recipe meets timing with a
small positive Worst Negative Slack, then the Step 3 sweep runs every recipe at that
fixed period. Generated by `harness/calibrate_clocks.py`, 2026-09-18.

## Method

- **Fixed-point search on full-route Worst Negative Slack.** The achievable data-path
  delay is roughly period minus Worst Negative Slack, so period_next = period minus
  Worst Negative Slack drives the slack toward zero; a 2% margin biases it slightly
  positive so resyn2 comfortably meets timing. Each step is a full place-and-route
  (the only honest signal, since routing parasitics matter). The first step is seeded
  from the recorded resyn2 baseline to save iterations.
- **All-clock scaling for a design whose binding path is not the core clock.** ethmac
  is multi-clock; its critical path is on the tx clock (300 ps), not the core clock.
  Scaling only the core clock never moved its slack, so ethmac is calibrated by
  scaling every clock domain by a common factor (`--scale-all`).
- Single-clock designs and multi-clock designs whose binding path is the core clock
  (mock-cpu) use plain core-clock scaling.

## The riscv32i caveat

riscv32i's post-route Worst Negative Slack is non-monotonic in the clock period:
relaxing it further makes timing worse, not better (1138 ps gives -3.89 ps, but 1165
ps gives -16.84 and 1205 ps gives -50.24), and a separate run put 1036 ps at -0.57.
It has many balanced near-critical paths, so small period changes reshuffle which
path is critical, giving roughly +/- 50 ps of period-sensitivity noise. No single
period reliably crosses to positive slack. We keep its tightest achieved point, 1138
ps (-0.34%, essentially at the wall), and flag it. Whether riscv32i's area numbers
are stable enough to keep in the headline is deferred to the Step 3 data: the sweep
runs many recipes, so we can judge from the distribution rather than one point.

## Why the operating clock is the wall, not a looser "margin" clock

A first attempt set the operating clock to a looser period aiming for ~10% positive
slack (operating = delay / 0.90). That was wrong, and a probe caught it: at aes's
looser 430 ps clock, resyn2 came out at -20.85 ps (-4.8%), **missing** timing,
although it met with +1.31 ps at its 388 ps wall.

The cause is a real, well-known OpenROAD behavior: **the flow optimizes only as hard
as the target demands.** Loosen the clock and it backs off on cell sizing and
buffering, so the achieved delay grows to fill the slack (and can overshoot into a
miss). Delay is not constant in the target period, so "delay / 0.90" does not buy
margin. The tool eats it.

Consequently the honest matched-delay operating point is the **wall clock**: the
period at which resyn2 sits at Worst Negative Slack ~ 0 by measurement (the table
above). That is where the label sweep runs.

The separate worry that motivated the looser clock (few non-resyn2 recipes meet
timing at the wall) is not a clock problem. It is that random search is a weak
optimizer against a tuned resyn2. The fix for that is a better search (the
predictor-guided search), not a looser clock, which would only hide the real signal.

## Consumption

`results/clocks.json` holds the operating period (= wall period) and mode per
design; `wall_period` / `wall_wns` are kept for provenance. The label sweep reads it
and passes the matching SDC (Synopsys Design Constraints) override so every recipe on
a design runs at its wall period.
